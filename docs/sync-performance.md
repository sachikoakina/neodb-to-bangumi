# 增量同步性能诊断与优化方案

本文诊断「增量同步过慢」的成因，并给出在不引入并发前提下可落地的优化方向。所有代码引用基于**改造前基线** `4188c31`；优化已于 2026-11-09 按第 6 节的 O1/O2/O3/O5/O6/O7/O8/O9/O10 落地（见第 10 节），因此行号已漂移——按函数名定位，不要按旧行号。O4 与 O11 刻意未实现。

**本文不包含实测数据。** 仓库内没有 `.cache/` 与 `.env`，无法读取真实的书架规模与报告产物，因此文中数字分两类：**实测口径**（第 1 节给出的命令与字段）与**模型推算**（第 4、7 节的算式与结果）。推算依赖的假设全部列在附录 B，每个结论在第 5.2 节给出反证条件。

## 0. 结论摘要

1. **瓶颈不是「同步逻辑」，而是「分集拉满的逐集 PUT」**。`SYNC_PROGRESS=1` 下，一条 12 集全缺的 TV 条目墙钟约 10.0 秒，其中 **78% 花在 12 次单集 PUT 上，其中 4.8 秒是纯 `sleep`**。
2. **固定等待与网络耗时是「相加」而不是「取最大」**。`bangumiThrottle()` 内部是 `sleep(400)`，且在请求**前**调用、在条目**尾部**再调用一次；单请求有效周期 = `400ms + RTT ≈ 650ms`，而不是 `max(400, RTT) = 400ms`。
3. **同一件事被睡了三遍**：分集列表翻页前睡、分集状态翻页前睡、每集写入前睡、条目尾部再睡一次（`src/clients/bangumi.ts:186,231,278` 与 `src/paths/neodb-to-bangumi.ts:277`）。最后那一次在分集条目上是重复计费。
4. **机制层有三处缺口，比「慢」更值得修**：
   - `unresolved` / `failed` 不写增量指纹 → 未匹配条目**每天**重做一遍完整匹配（NeoDB 详情 + 最多 3 次搜索 + N 次候选详情）。
   - **分集进度不在指纹里，而增量门在 `processMark` 之前** → 一旦某条目被记成「已同步」，之后再开 `SYNC_PROGRESS=1` 也补不上分集，只能 `FULL_SYNC=1`（无预算、无增量）重跑。这是「越跑越慢」体感的主要来源。
   - 吞吐被 `SYNC_MAX_ITEMS=50` 钉死：单轮再快也只推进 50 条，积压只能按天消化。
5. **零并发下的收益来源是「减少请求数」，不是「加快请求」**。去掉重复读取、把年份读取后移、复用缓存、给未匹配条目加指数退避、分集分批——每一步都同时降低耗时与请求压力，语义不变。
6. **全局「固定节拍」限流器是把双刃剑**：对分集条目 -36%，但对「请求少而密」的标题匹配条目是**负收益**（1.9s → 2.4s）。所以它列为可选档，而不是默认建议。

## 2. 增量同步机制现状

### 2.1 一轮运行的时序

```
凭据探测（1 次 NeoDB /api/token，1 次 Bangumi /v0/me）
└── for 每个书架（默认 4 个）
    ├── for 每页（常规最多 10 页，页间 sleep 300ms）      ← 每页 1 次 NeoDB 请求
    │   ├── 页内按「状态强度 + uuid」排序                src/paths/neodb-to-bangumi.ts:229-235
    │   └── for 每条
    │       ├── 指纹命中且未 FULL_SYNC → skipped，不消耗预算   :239-247
    │       ├── 预算耗尽 → 停止本书架，不算截断                :248-253
    │       └── processMark()                              :342-624
    │           ├── 分类白名单 / 支持性判定                    :363-371
    │           ├── 匹配：外链 → 标题搜索 → 证据裁决            :374-390, 724-850
    │           ├── 目标认领：重复目标让给更强认领者            :407-429
    │           ├── 读收藏（失败绝不当 absent）                :432-436
    │           ├── 状态映射 + 字段合并 + 隐私规划              :439-495
    │           ├── 书籍进度（随 upsert 同请求）                :497-524
    │           ├── upsert（仅在有差异时）                      :563-575
    │           ├── 分集拉满（独立请求）                        :586-597
    │           └── 落指纹 / 失败清指纹                         :599-623
    └── 书架结束：写一次 state（若脏）                          :304-307
```

### 2.2 指纹构成与跳过时机

`fingerprintMark`（`src/sync-config.ts:332-344`）为：

```
sha1( uuid | shelf_type | rating_grade ?? 0 | comment_text ?? '' | visibility ?? '' )
```

含 **5 个字段**，不含：Bangumi `subjectId`、`external_resources`、分集进度、`tags`。

跳过发生在 `src/paths/neodb-to-bangumi.ts:239-247`，**在整页取回之后、`processMark` 之前**。由此得到两个必要认知：

- 稳态下每轮仍要为每个书架付分页成本，但**不会**为已同步条目付任何 Bangumi 请求。这是设计意图，也是「日常扫描本来就不慢」的原因（见 5.3）。
- 跳过是**硬跳过**，不进入 `processMark`，因此**不检查分集**。

### 2.3 预算与页数上限的相互作用

- `budgetUsed` 只在真正进入处理流程时自增（`:215, 248-253`），指纹跳过的条目不消耗预算——这一点是正确的，否则定时任务会每天在前 50 条已同步条目上原地打转。
- 但预算一旦耗尽就 `return false` 停止该书架（`:249`），**后续书架整轮不遍历**。所以「每天 50 条」是全局吞吐上限，不是每个书架各 50 条。
- 常规运行不读全量游标（`:207-209`），永远从第 1 页开始——新标记在第 1 页，这是对的。

### 2.4 全量游标

`FULL_SYNC=1` 且非 dry-run 时才读写（`:206-209`）。每页处理完写一次（`:283-297`）；主动停止（含认证中止、预算耗尽）把游标指回当前页（`src/clients/neodb-shelf.ts:148-151`），续跑整页重走，靠写入幂等兜底。

### 2.5 三个机制层缺口

| 缺口                   | 位置                                                  | 后果                                                                                     |
| ---------------------- | ----------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| `unresolved` 不留指纹  | `:384-390` 返回前无 `rememberState`                   | 未匹配条目**每轮**重做完整匹配，永不衰减；真人影视覆盖率低的账号这部分是每日固定浪费     |
| `failed` 无退避        | `:375-383`，仅 `forgetState`（`:608`）                | 设计上正确（下轮可重试），但没有任何退避上限，持续失败的条目每轮都在打                   |
| **分集进度不在指纹里** | 指纹 `src/sync-config.ts:332-344` + 硬跳过 `:239-247` | 条目一旦被记「已同步」，之后开启 `SYNC_PROGRESS=1` 也不会补分集；只能 `FULL_SYNC=1` 重跑 |

关于第三点需要特别说明：`docs/mapping.md:42` 写的是「收藏的状态/评分/短评/隐私完全一致时，仍会读取分集并补齐缺口」。这句话在**单次 `processMark` 内部**成立（`:582-597` 是独立分支，不挂在 `differs` 上），但增量门在它之前就把条目挡掉了。因此准确表述应为：**该条目本轮的收藏字段无变化时仍会检查分集；但上一轮已把指纹写死的条目不会**。这不是 bug，但它让「先跑通再开进度」的两阶段用法失效——而两阶段恰恰是最自然的用法。第 6 节的 O5 就是补这个缺口。

## 3. 单条请求扇出

### 3.1 请求清单（按分支穷举）

| 阶段      | 请求                                          | 位置                                 | 何时发生                                        |
| --------- | --------------------------------------------- | ------------------------------------ | ----------------------------------------------- |
| 匹配·外链 | 无                                            | `:726-735`                           | NeoDB 条目带 `bgm.tv/subject/{id}` 外链         |
| 匹配·年份 | `GET {item.api_url}`（NeoDB）                 | `:742, 903`                          | 无外链且书架列表无 `year/pub_year`              |
| 匹配·搜索 | `POST /v0/search/subjects`                    | `:756`, `src/clients/bangumi.ts:321` | 每个标题候选 1 次，最多 3 次                    |
| 匹配·证据 | `GET /v0/subjects/{id}`                       | `:863`, `src/clients/bangumi.ts:65`  | 每个精确同名候选 1 次，仅 `isYearFilterType`    |
| 读收藏    | `GET /v0/users/{u}/collections/{id}`          | `:432`                               | 每条必发                                        |
| 写收藏    | `POST /v0/users/-/collections/{id}`           | `:565`                               | 仅在有差异或书籍进度待写时                      |
| 书籍进度  | `GET /v0/subjects/{id}`                       | `:505`                               | complete 书籍且 `SYNC_PROGRESS=1`；**绕过缓存** |
| 分集列表  | `GET /v0/episodes`                            | `:960`                               | complete 影视且 `SYNC_PROGRESS=1`               |
| 分集状态  | `GET /v0/users/-/collections/{id}/episodes`   | `:979`                               | 同上                                            |
| 分集写入  | `PUT /v0/users/-/collections/-/episodes/{id}` | `:1021`                              | 每个缺失集 1 次                                 |

两个可以立刻指出的浪费：

1. **`:505` 绕过了 `subjectCache`**。候选证据读取（`:863`）与书籍进度读取可能是同一个 subject，`readSubjectCached` 会缓存，但 `:505` 直接调 `getBangumiSubject`，构成第二次 GET。
2. **年份读取被放在搜索之前**（`:742`）。`resolveItemYear` 在任何搜索发出前就执行，因此「搜不到任何精确同名候选」的条目也白付一次 NeoDB 详情请求——而这类条目恰恰每轮都会重来（见 2.5）。

### 3.2 三档典型画像

设 `r=250ms`、`d=400ms`，分页数为 1。

| 画像       | 条件                               | 请求数 | 固定 sleep 次数 | 墙钟                       |
| ---------- | ---------------------------------- | ------ | --------------- | -------------------------- |
| A 稳态     | 外链命中，收藏字段无变化           | 1      | 1               | `250 + 400` = **0.65s**    |
| B 字段变更 | 外链命中，评分/短评有差异          | 2      | 1               | `500 + 400` = **0.90s**    |
| C 标题匹配 | 2 个标题候选、2 个精确候选，无差异 | 6      | 1               | `1500 + 400` = **1.90s**   |
| D 分集拉满 | complete TV，12 集全缺，字段有变更 | 16     | 15              | `4000 + 6000` = **10.00s** |
| E 书籍进度 | complete 书籍，字段有变更          | 3      | 1               | `750 + 400` = **1.15s**    |

画像 C 的 6 次 = 1 NeoDB 详情 + 2 搜索 + 2 候选详情 + 1 收藏读取。
画像 D 的 16 次 = 1 收藏读取 + 1 收藏写入 + 1 分集列表 + 1 分集状态 + 12 单集 PUT；15 次 sleep = 列表翻页 1 + 状态翻页 1 + 逐集 12 + 条目尾部 1。

### 3.3 叠加等待的准确算式

当前实现里 `bangumiThrottle()` 只做 `sleep(d)`（`src/clients/bangumi-http.ts:41-43`），调用点全部在请求**之前**（`src/clients/bangumi.ts:186,231,278`）或条目**之后**（`src/paths/neodb-to-bangumi.ts:277`）。因此：

```
单请求有效周期 = d + r          （不是 max(d, r)）
单条墙钟      = Σr_i + Σd_j
```

以画像 D 为例，`n` 集时：

```
T_D(n) = (n + 4) · r + (n + 3) · d
       = (n + 4) · 250 + (n + 3) · 400        (ms)
       = n · 650 + 2200
```

验算：`n=12` → 10000ms；`n=24` → 17800ms；`n=50` → 34700ms。

## 4. 各环节耗时分解

### 4.1 画像 D（12 集）的阶段拆分

| 阶段                            | 请求数 | RTT 小计 | 固定等待 |     小计 |       占比 |
| ------------------------------- | -----: | -------: | -------: | -------: | ---------: |
| 数据获取（书架分页，均摊）      |      — |        — |        — |        — | 单列于 4.2 |
| 匹配（外链命中，本项目 0 请求） |      0 |        0 |        0 |        0 |         0% |
| 字段映射（纯 CPU）              |      0 |        0 |        0 |        0 |        ≈0% |
| 收藏读取                        |      1 |      250 |        0 |      250 |       2.5% |
| 收藏写入                        |      1 |      250 |        0 |      250 |       2.5% |
| 分集列表 + 分集状态             |      2 |      500 |      800 |     1300 |      13.0% |
| **分集逐集写入**                |     12 |     3000 |     4800 | **7800** |  **78.0%** |
| 条目尾部节流                    |      0 |        0 |      400 |      400 |       4.0% |
| 合计                            |     16 |     4000 |     6000 |    10000 |       100% |

关键读数：**60% 的墙钟是 `sleep`，不是网络**；而 `sleep` 的 80% 来自逐集 PUT。

### 4.2 纯 CPU 环节的位置与量级

字段映射与判定全部是纯函数，无 I/O：

- `mergeRating` / `mergeComment` / `planBangumiPrivate`（`src/rules/neodb-bangumi-mapping.ts`）
- `shouldSkipClaim`（`src/rules/target-claim.ts`）
- `planEpisodeProgress` / `planBookProgress`（`src/rules/bangumi-progress.ts`）
- `decideWriteOutcome`（`src/rules/write-decision.ts`）
- `pickExactMatch` / `exactMatches`（`src/rules/neodb-bangumi-matching.ts`）

量级：每条目几十次字符串比较与一次 SHA1（`src/sync-config.ts:332-344`），微秒级。50 条合计不足 1ms，**不构成瓶颈**。另外 `fingerprintMark` 每条被算了两次（`:242` 判定、`:349` 处理），属可忽略的微冗余，列出仅为说明该项已被检查过。

真正需要注意的是 `consola` 的同步 stdout 写入：每条目多条 `info` 行，CI 下会写日志文件。50 条约 200 行，量级远低于任何网络请求；但如果将来放开预算到数千条，应换成带采样的批量输出。

### 4.3 书架遍历成本

```
T_shelf = N_page · r + (N_page − 1) · d_n        src/clients/neodb-shelf.ts:170
```

`NEODB_MAX_PAGES=10`、`d_n=300`、`r=250` → 每书架 `10×250 + 9×300 = 5.2s`，4 个书架约 **20.8s**。这是稳态每轮的固定成本，与「慢」无关，但它是「至少也要跑二十几秒」的下限。

### 4.4 对 RTT 的敏感性

|   `r` | 现状单请求周期 | 12 集条目 | 400 条 complete TV 纯分集耗时 |
| ----: | -------------: | --------: | ----------------------------: |
| 150ms |          550ms |      8.8s |        5200 × 0.55 ≈ 47.7 min |
| 250ms |          650ms |     10.0s |        5200 × 0.65 ≈ 56.3 min |
| 400ms |          800ms |     12.4s |        5200 × 0.80 ≈ 69.3 min |

（假设 400 条 complete TV、平均 13 集全缺 = 5200 次 PUT。）

这张表说明一件事：**现状下 RTT 直接放大总时长**。若把限流改成「请求起点间隔」，周期收敛到 `max(d, r) = d = 400ms`，在上面三档里都固定为 400ms——这也是第 7.3 节「档 B + O11」数字不随 RTT 变化的原因。

## 5. 瓶颈判定

### 5.1 排序与依据

| 排序 | 瓶颈                         | 依据                                                                          | 影响面                                |
| ---: | ---------------------------- | ----------------------------------------------------------------------------- | ------------------------------------- |
|    1 | 分集逐集 PUT 的叠加等待      | 画像 D 中 78% 墙钟、60% 为 sleep（4.1）；`n·650 + 2200` 线性增长              | 仅 `SYNC_PROGRESS=1` 且 complete 影视 |
|    2 | 标题匹配的多请求扇出         | 画像 C 6 次请求，其中 3 次可能在「搜不到」时白付（年份前置 + 无候选详情）     | 无外链条目                            |
|    3 | 未匹配条目每日重复匹配       | `:384-390` 不留指纹 → 每轮重付 4–6 次请求                                     | `unmatched.json` 规模决定             |
|    4 | 每日 50 条预算形成的吞吐上限 | `src/sync-config.ts:240`、`:248-253`                                          | 所有积压场景                          |
|    5 | 分集进度无法通过增量补齐     | 指纹不含进度 + 硬跳过 `:239-247`                                              | 先开同步、后开进度的用户              |
|    6 | Bangumi 侧无重试             | `src/clients/bangumi.ts` 全部裸 `got`；对照 `src/clients/neodb-http.ts:26-38` | 抖动即整条作废一天                    |
|    7 | 无耗时埋点                   | `PathReport` 只有 5 个计数（`src/sync-report.ts:15-22`）                      | 无法定位，只能靠猜                    |

第 5 项在某些账号上会升到第 1：如果历史条目都已记指纹且 `SYNC_PROGRESS` 后开，那么**增量永远不会碰它们**，唯一出路是 `FULL_SYNC=1`（无预算、无增量、180 分钟上限）。此时用户感受到的是「一开进度就全量重跑，慢到超时」。

### 5.2 每条结论的反证条件

| 结论                 | 反证条件（若成立则结论不成立）                           |
| -------------------- | -------------------------------------------------------- |
| 分集 PUT 是主因      | 单轮 `sleep` 总量占比 < 30%，或 `missing=0` 的条目占多数 |
| 标题匹配扇出是次因   | `match-audit.json` 中 `via=link` 占 > 90%                |
| 未匹配条目是固定浪费 | `unmatched.json` 条数 < 扫描数的 5%                      |
| 预算才是真瓶颈       | `scanned` 长期远小于 50（说明没打满，慢在别处）          |
| 稳态扫描不慢         | 单轮墙钟里书架分页 > 50%                                 |
| 分集进度被增量锁死   | 打开 `SYNC_PROGRESS=1` 后 `分集进度:` 日志行数显著增加   |

### 5.3 反直觉结论：日常扫描并不慢

指纹命中即硬跳过（`:239-247`），已同步条目只付书架分页。稳态单轮成本 ≈ 20.8s（4 书架 × 10 页）+ 少量变更条目。因此：

- 如果「每天跑一次很慢」，那一定是因为**变更条目多**（评分/短评批量整理）、**分集缺口大**（刚开 `SYNC_PROGRESS`）、或**未匹配条目多**（真人影视），而不是分页。
- 如果「跑完还差很多条」，那是**预算**问题（第 4 位瓶颈），不是速度问题。这两件事必须分开修。

### 不做的事

- **不合并/不批量化收藏 upsert**：v0 没有批量收藏端点，且每条的 payload 不同。
- **不降低 `SYNC_MATCH_STRICT`**：那会牺牲正确性换速度，与本项目的取舍（宁可漏配，不可错配）冲突。
- **不缩短 `NEODB_REQUEST_DELAY_MS`**：书架分页只占稳态 20.8s，收益有限，且是 NeoDB 侧唯一的节流保护。

## 7. 优化前后对比

口径：`r=250ms`、`d=400ms`、分页 1 页；`SYNC_PROGRESS=1`；两档均保持零并发。

- **档 A（保守）**：O2 + O3 + O10，请求数与周期口径不变，只减重复请求与重复等待。
- **档 B（中性）**：档 A + O5 + O7(a,b) + O8，改的是「哪些条目值得处理」与「单条做多少」，仍是串行。
- 不在两档内计入 O4（跨轮缓存）与 O11（节拍），前者收益取决于重复度，后者有速率风险。

| 单轮被 60 分钟 timeout 杀掉的风险                  | 中（全量时高：约 56 min 纯分集 + 15 min 条目开销 ≈ 71 min） |           中 | 低（45 分钟预算主动停，正常落盘） |

档 A 的诚实结论：**单轮只快 3–4%，天数不变**。因为它的收益集中在「未匹配条目」与「书籍」，而积压场景的主体是分集。真正改变天数的是档 B 的两件事——O5 让分集能被增量补齐（不必全量）、O8 让单轮吃满时间窗口（不必被 50 条卡住）。

## 8. 验证方式

原则：**先用 dry-run 证明「结论不变」，再用小批量证明「写入不变」，最后才放开**。全程不需要改代码，也不需要清空任何产物。

### 8.0 前置条件：能直连两个 API

验证的前提是能访问 `https://neodb.social` 与 `https://api.bgm.tv:443`。两步自检：

```bash
node -e "const t=async u=>{const s=Date.now();try{const r=await fetch(u);console.log(u+' -> HTTP '+r.status+' ('+(Date.now()-s)+'ms)');}catch(e){console.log(u+' -> ERR '+(e.cause&&e.cause.code?e.cause.code:e.message)+' ('+(Date.now()-s)+'ms)');}};(async()=>{await t('https://neodb.social/api/token');await t('https://api.bgm.tv/v0/me');})();"
npm run probe:neodb
```

| 现象                                         | 含义                       | 处理                    |
| -------------------------------------------- | -------------------------- | ----------------------- |
| `HTTP 402` / `HTTP 401`                      | 网络通，令牌无效或过期     | 重新授权令牌            |
| `ERR_UND_ERR_CONNECT_TIMEOUT`、`no response` | **传输层不通**，与令牌无关 | 查 DNS / 网络，别换令牌 |
| 域名解析到与自己无关的网段                   | 可能是 DNS 污染或代理劫持  | 换网络或走 CI           |

注意：本仓库的 Bangumi 与 NeoDB 客户端都没有配置 `agent`，而 `got` 不读取 `HTTP(S)_PROXY`，因此**系统代理不会生效**——只挂系统代理而没开 TUN/全局模式的机器上会稳定超时。这类环境请直接用仓库自带的 Actions 工作流跑验证（Secret 注入，`.github/workflows/sync.yml:47-48`）。

### 8.2 等价性断言（最关键）

改动前后各跑一次全量 dry-run，把审计写到不同文件：

```bash

```

然后逐条比对五元组：

```bash
node -e "
const fs=require('fs');
const key=p=>JSON.parse(fs.readFileSync(p,'utf8')).entries
  .map(e=>[e.uuid,e.subjectId,e.via,e.outcome,e.reason].join('|')).sort();

console.log('before='+a.length+' after='+b.length+' diff='+(onlyA.length+onlyB.length));
if(onlyA.length) console.log('仅旧:',onlyA.slice(0,10));
if(onlyB.length) console.log('仅新:',onlyB.slice(0,10));
process.exitCode=(onlyA.length+onlyB.length)?1:0;
"
```

判定标准：

| 检查项                  | 通过条件                                                                             | 备注                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| 审计五元组              | 仅允许一类差异：`failed(bangumi-year-fetch-failed)` → `unresolved(no-bangumi-match)` | 其余任何 `(uuid, subjectId, via, outcome, reason)` 不同都算回归（见 O3 风险）；`sourceYear` 不纳入比对 |
| `written` 计数          | 前后一致                                                                             | dry-run 下 `written` 是计划数                                                                          |
| `unmatched.json` 键集合 | 不减少（除 `REVIEW_STATE_MAX_AGE_DAYS` 老化）                                        | dry-run 写到 `unmatched-dryrun.json`，不污染正式文件                                                   |
| 报告恒等式              | `scanned = written + unchanged + skipped + unresolved + failed`                      | `assertReportInvariant`（`src/sync-report.ts:33-42`）必须为真                                          |

注意事项：dry-run 不写 state（`rememberState` 在 `:626-632` 直接返回）、不写全量游标（`cursorPath` 在 `:207-208` 为空），所以等价性测试是**无副作用**的，可以反复跑。

## 9. 未采纳方案：跨条目并发

明确不选，理由不是「保守」，而是它会破坏当前三处依赖串行的契约：

1. **目标认领的裁决时序**。页内先按「状态强度 + uuid」排序（`:229-235`），认领在读完收藏后才登记（`:461`），落败者记 `skipped` 并进待核对（`:414-429`）。并发下两条目录可能同时通过认领检查，导致同一 subject 被写两次、强弱裁决失效。
2. **认证中止的传播**。`AuthAbortError` 在单条内抛出（`:260-263`），外层通过 `ctx.aborted` 在循环头退出（`:218`）。并发下需要在途请求全部感知中止，否则会出现「已判定中止但仍在写」。
3. **状态落盘粒度**。state 按书架粒度落盘（`:304-307`），游标按页落盘（`:283-297`）。并发下两者都可能出现「已处理但未记录」，续跑语义需要重写。

要并发，必须先重写这三份契约（认领预占、中止栅栏、增量提交），风险远大于收益，且与本轮「零并发、最小风险」的前提冲突。

另外，即便实现并发，Bangumi 侧的总速率仍受节流器约束，**真正的加速来自减少请求数，而不是同时发**。这也是第 6 节把「去重、缓存、退避」排在「调时序」之前的原因。
